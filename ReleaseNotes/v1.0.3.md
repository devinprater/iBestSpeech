# iBestSpeech 1.0.3

Fixes faults in the speech engine that were found by sweeping every character
and character pair through all twenty builds, rather than by listening. All of
them are the same kind of defect: the voice still speaks, so nothing looks
broken, but it says the wrong thing or nothing at all.

## A number with a separator in it was silent

"5 19", "5/19" and "5,19" produced **no audio at all** — on every one of the
twenty builds, in every position. "Call 555 1234 now" was silent too, which is
how this one reaches real text: the failure took the whole utterance, not just
the numbers.

The cause is in the engine's state machine. A separator between two runs of
digits gets a state of its own, so the run arrives at one handler whole. That
handler could not read it, rejected it, and returned **without consuming it** —
so no handler was left, and the turn produced nothing. It retried the same
token until the guard expired. Each run is now read as its own number, which is
what the same text with a hyphen between the numbers already did.

## Words after a number with a comma were thrown away

On the thirteen 2006 builds, `3,4,5` did worse than fall silent: the build's
own first-group rule said the first group and **abandoned the rest of the
text**. `alpha 3,4,5 omega zeta` came out the same length as `alpha 3,4,5`.

A run whose comma-separated groups are a real grouped number — `1,000`,
`1,234,567` — keeps that rule, because it is what the original binaries do.
A run that is *not* a grouped number is a list of numbers, and no longer takes
the rest of the sentence with it.

## The app's own separator was making things worse

The app breaks up adjacent numbers (`555 1234`, which is silent) by inserting a
separator. It inserted a **comma** — and a comma is the exact character that
ends the text on the 2006 builds. So the app's workaround turned silence into
silent truncation on 65% of builds. It now inserts a **colon**, which is
byte-identical to a comma where a comma works (`hello, world` and `hello: world`
are the same 13839 samples) and keeps the tail on all twenty builds.

## The 1998 English digit faults are the hardware, not ours

Two things this release deliberately does **not** change, because they are
faithful reproductions of the original binaries:

- The digit-name, tens and teens table addresses. `tests/golden.txt` holds
  4906 answers taken from the original DLLs; the library reproduces every one
  of them, and moving those addresses shifts 13.
- The Arabic and Japanese digit silence. A bare `0` on the 1998 English build
  really is a 57075-sample sequence in the hardware. It is the app's job to
  avoid handing that build a zero, not the library's to pretend otherwise.

## Also fixed since 1.0.2

- A clock time (`5:19 PM`) speaks as a time. It used to be read as a decimal —
  "five point one nine" — from a full stop, and as nothing at all from the colon.
- A stop written straight against a digit (`Read.6:23 PM`, which is how an
  accessibility value often reads) no longer silences the utterance.
- The 1998 English build no longer reads a run of ten or less as a long garbage
  sequence.

## Verified

- The Swift `SSMLText` tests: **99/99**.
